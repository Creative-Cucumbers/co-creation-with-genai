# 第5回 プログラミング演習｜授業進行台本

**授業テーマ：作れるWebアプリの幅を広げよう！**  
**授業時間：100分×2コマ（合計200分、コマ間の休憩は別枠）**  
**構成：50分×4ブロック**  
**制作環境：Google AI Studio（想定）／Slack（進捗共有）**

> この文書はスライドの原稿ではなく、教員が授業を進めるための台本・進行計画である。時刻は授業開始からの経過分で示す。学生の操作時間にはSlack投稿を含める。

## 0. 授業の基本設計

### 今回のメッセージ

Webアプリで作れるものの幅は、**①入力の幅、②表現の幅、③データの幅**を広げることで大きくなる。新しい方法を知り、小さなアプリで試し、動作を確かめる。

- **① 入力の幅を広げる**：「何を受け取れる？」— マイクやセンサー、デバイスの情報。
- **② 表現の幅を広げる**：「どう反応する？ どう見せる？」— 入力・処理・出力の設計、画像素材の活用。
- **③ データの幅を広げる**：「どんな情報を使える？」— 外部APIから取得するデータ。

### 授業終了時の到達目標

1. マイクの情報を利用したWebアプリを動かし、デバイス情報の取得にブラウザのAPIが関わることを説明できる。
2. 「入力・処理・出力」の関係を用いて、音声やクリックに反応する動作を考え、アプリへ反映できる。
3. 画像生成用の指示を考えて素材を改良し、それを使う簡単なインタラクティブアプリを作れる。
4. JSONの基本構造を読み、外部APIの情報を取得して使う小さなWebアプリを作れる。
5. 次回・次々回の自由制作に向けて、作りたいアプリのアイデアを3つ以上挙げられる。

### 制作物の関係

- **アプリA（第1・2ブロック）**：共通の音声波形アプリを出発点に、音やクリックで変化する動作を追加する。
- **アプリB（第3ブロック）**：生成した画像素材から始める**別アプリ**。見た目を丁寧に指定し、簡単な入力で反応させる。
- **アプリC（第4ブロック）**：選んだ外部APIを利用する**別アプリ**。データの取得と表示を優先する。

### 授業運営の共通ルール

- 一つの演習につき、「目的提示 → 実演または指示 → 学生が制作・確認 → Slack投稿 → 次へ」を基本形にする。
- 投稿は**画面＋一文**を基本とし、文章作成に時間をかけすぎない。
- 完成しない学生も、**できたこと・困っていること**を投稿してよい。
- 演習の基本達成条件と、時間が余った学生向けの発展を区別する。
- AIの出力は実機で検証する。生成しただけでは完成とみなさない。

## 2. 第1ブロック（0〜50分）｜① 入力の幅を広げる

### 0–5分｜アイスブレイク

**教員の狙い**：今回の「入力」を身近な経験から考えてもらう。

**話すこと（例）**

> 今日からは、作れるWebアプリの幅を広げていきます。まず、普段使うアプリを思い出してください。タップや文字入力以外に、アプリはどんな情報を受け取っているでしょう？

**学生の活動**：身近なアプリ1つと、そこに使われる入力を考える。

**Slack投稿**：「アプリ名：／利用している入力：」の2項目。

**つなぎ**：「前回作ったWebアプリはどんな仕組みで動いていたか、図で振り返ります。」

### 5–17分｜前回の復習：Webアプリ構造図

**準備**：前回使用した構造図をもとに、名称を一部隠した穴埋め版。候補として「ブラウザ・画面」「Webサーバー」「バックエンド／API」「Firestore」「Authentication」などを用意する。

**進行**

- 5–8分：個人でカードやラベルを配置。
- 8–11分：近くの学生と比較。
- 11–15分：全体で答え合わせ。前回作成したToDo・チャットアプリの要素がどこに当てはまるかを確認。
- 15–17分：前回の開発サイクル「アイデア → AIに指示 → 生成 → 動作確認 → 修正 → 理解」を短く振り返る。

**教員の確認質問（例）**

- 前回の画面は、どこで動いていた？
- Firestoreは何を保存していた？
- Authenticationは何のために使った？
- AIが作ったら、そのまま完成と言える？

**留意点**：Firebaseを使う場合、ブラウザからFirestoreやAuthenticationへSDK経由で通信する構成もある。常に自前のAPIサーバーを経由するかのように説明しない。

### 17–23分｜今日のゴールと道順

**話すこと（例）**

> 前回はWebアプリの基本構造と、データの保存・認証を学びました。今日はこの構造を土台に、①何を受け取るか、②どう反応・表現するか、③どんな外部データを使うか、という3つの方向で作れるアプリの幅を広げます。

構造図に「マイク・センサー」「表現・表示」「外部サービス」の要素を描き足し、4つの50分ブロックを紹介する。

**到達目標**：今回の3テーマを学生が短く言い換えられること。

### 23–38分｜①-1 共通演習：音声波形アプリ

**目的**：PCのマイクから音声を取得し、Webアプリ上で波形が動くことを体験する。

**話すこと（例）**

> 最初は全員でほぼ同じアプリを作ります。難しい見た目の工夫は不要です。声を出すと波形が変わることを確認してください。

**共通プロンプト案**

```text
PCのマイクから入力された音をリアルタイムで可視化するWebアプリを作ってください。
マイクの開始・停止ボタンを用意し、音声の波形を画面に表示してください。
マイクの使用許可がない場合や利用できない場合には、状態が分かるメッセージを表示してください。
音声を録音・保存・外部送信する必要はありません。ブラウザ内で処理してください。
```

**進行の目安**：2分でデモ・指示、10分で生成・試行、3分で動作確認・投稿。

**完成条件**：マイクの許可を与え、声や音に応じて波形が変化する。停止操作も確認する。

**Slack投稿**：波形アプリの画面＋「声を出すと何が起こったか」を1文。

**困った学生への対応**：マイク・ブラウザ権限、HTTPS等の安全な実行環境、マイクの接続状態を確認。利用できなければ教員デモで構造を理解し、「未動作・原因」を投稿してよい。

### 38–43分｜ブラウザAPIの仕組み

**見せる図**：「PCマイク → ブラウザのAPI → 音声の解析 → 波形表示」。

**話すこと（例）**

> AIが魔法のように音を取っているわけではありません。Webアプリはブラウザの機能を使ってマイクへアクセスし、得た音声を処理して波形として表示しています。

**用語の扱い**：マイク入力には主に `navigator.mediaDevices.getUserMedia()`（MediaDevices API）、波形解析にはWeb Audio APIなどを利用する。加速度などを扱うGeneric Sensor APIとは同一ではないので、「センサー関連のブラウザAPI」と大きく捉えつつ区別する。

### 43–48分｜センサーの応用例

**短く紹介する例**：スマホの加速度・ジャイロ、スマートウォッチの運動・心拍関連センサー、動きで操作するゲームなど。

**教員の問い**：「こうした情報を使えば、どんなWebアプリや製品が考えられそう？」

**ポイント**：デバイスにセンサーが存在することと、すべてのブラウザから同様に使えることは別。端末・OS・権限によって取得できる情報は異なる。

### 48–50分｜まとめ・次への接続

**話すこと（例）**

> いまは音を波形にしました。でも同じ音の情報を使って、花を咲かせたり、風船を膨らませたりできるはずです。次は、入力をどう表現に変えるかを考えます。

## 3. 第2ブロック（50〜100分）｜② 表現の幅を広げる：反応を設計する

### 50–58分｜入力・処理・出力という考え方

**例A：音声波形アプリ**

- 入力：マイクの音声。
- 処理：取得した音声から波形の値を取り出す。
- 出力：波形を描画する。

**例B：風船アプリ**

- 入力：マイクに向かって息を吹きかける音。
- 処理：音の強さに応じて風船の大きさを決める。
- 出力：画面の風船が膨らむ。

**話すこと（例）**

> 入力が同じでも、処理と出力を変えると別の体験になります。今日は「何が起きると、何がどう変わるか」を自分で決めてみます。

**補足**：マイクから直接「息の量」を測るわけではなく、音の強さを利用した演出である。

### 58–65分｜②-1 音で何を変える？（アイデア）

学生は、アプリAの音声入力を使って何を変えるか、**入力・処理・出力**の3つで考える。教員例は「息を吹くと風船が膨らむ」。学生は同じ例を採用してもよい。

**Slack投稿**：「入力：／処理：／出力：」各1行。

### 65–78分｜②-2 音に反応する動作を実装

**学生の活動**：アプリAをAI Studioで改良し、波形表示を残したまま、音に反応するオブジェクトを追加する。

**追加指示例**

```text
今ある音声波形アプリの機能は残したまま、音の大きさに応じて画面の風船が膨らんだり縮んだりする表現を追加してください。
マイクを停止した場合の表示も適切にしてください。
```

学生は自分のアイデアに応じて対象や変化を変更してよい。

**完成条件**：音の変化によって、波形以外のオブジェクトにも変化が起きる。

**Slack投稿**：動作している画面＋「何が入力で何が変化したか」。

### 78–84分｜②-3 クリック・スクロールで何を変える？（アイデア）

**教員の問い**

> 今は音に反応するだけです。ここにクリック、ドラッグ、スクロールを追加したら、何ができそうでしょう？

**アイデア例**：クリックで風船の色を変える、ドラッグで風船を移動する、スクロールで高さを変更する。

**Slack投稿**：追加する入力と、変化させる内容を1〜2行。

### 84–96分｜②-4 複数の入力を組み合わせる

**学生の活動**：音声による反応を保持し、クリック／ドラッグ／スクロールのいずれか1つを追加する。

**完成条件**：異なる2種類の入力で、それぞれ何らかの動作が確認できる。

**Slack投稿**：追加した操作が分かる画面＋「音では○○、クリックでは○○」のような説明。

**補足**：スクロール量の取得はページの構成によって扱いにくい場合があるため、クリック・ドラッグも同列の選択肢とする。

### 96–100分｜②（反応）のまとめ

**確認質問**：「自分のアプリの入力・処理・出力を、他人に1分で説明できますか？」

**話すこと（例）**

> アプリの反応を考えるときには、まず入力、処理、出力に分けて考えると、AIにも具体的に指示しやすくなります。次は『どう動くか』から『どう見えるか』へ進みます。

## 4. 第3ブロック（100〜150分）｜② 表現の幅を広げる：見た目を設計する

### 100–107分｜見た目をもっとよくするには？

**出発点**：第1・2ブロックのアプリは動くが、見た目が必ずしも自分のイメージどおりではない。

**話すこと（例）**

> 「風船を表示して」とAIに指示するだけでは、見た目が思いどおりにならないことがあります。今回は、先に画像を作り、素材として使う方法を試しましょう。

**方針**：ここからは**別アプリB**。前半の機能を無理に引き継がず、見た目とインタラクションをつなぐ小さな作品を作る。

### 107–113分｜画像生成プロンプトの考え方

**説明する要素**：主題、色、形、構図、背景、素材の切り分け（キャラクター／背景等）。

**例**：「花の画像」→「透明背景、1本の花、正面から見た平面的なイラスト、淡い色、中心配置」のように具体化する。

**補足**：迷ったら自然（花・海・森・風・星など）から発想してよい。自然は形や動きの変化を考えやすい。

### 113–121分｜②-5 画像生成プロンプトを作る

**学生の活動**：1つの素材を選び、プロンプトを作成する。「何の画像で、アプリのどこに使いたいか」も考える。

**Slack投稿**：画像生成プロンプト＋使い道を1行。

### 121–134分｜②-6 画像を生成・改良する

**学生の活動**：画像を生成し、結果を見て修正点を伝え、再生成する。少なくとも1回は見た目の変更を指示する。

**完成条件**：アプリに使いたい画像1枚を選べること。

**Slack投稿**：採用画像＋何を修正したか1文。

**時間管理**：完全に納得するまで無制限に繰り返すのではなく、134分でアプリ化へ進む。画像の改良は余裕があれば継続する。

### 134–145分｜②-7 画像を使った別アプリBを作る

**学生の活動**：生成画像を画面に配置し、クリック・音声・ドラッグなどの入力で反応を追加する。

**完成条件**：素材がアプリに表示され、少なくとも1種類の入力で変化すること。

**Slack投稿**：アプリ画面＋入力による変化の説明。

**補足**：素材全体を動かすだけでも十分。画像の一部だけを動かすなら透過素材やパーツ分けが必要になる場合がある。

### 145–150分｜応用紹介・②のまとめ

**短いデモ**：画像パーツを組み合わせたアニメーション、簡単な3D表現など。

**話すこと（例）**

> 同じ「入力 → 処理 → 出力」の考え方でも、素材の工夫や3D表現によって、見た目の幅はさらに広がります。次は、アプリが使う情報そのものの幅を広げます。

## 5. 第4ブロック（150〜200分）｜③ データの幅を広げる

### 150–158分｜外部APIの導入・候補紹介・注意点

**図で示すこと**：「自分のWebアプリ ↔ 外部API ↔ 外部サービスのデータ」。前回のWebアプリ構造図に外部サービスを追加する。

**話すこと（例）**

> これまではマイクやクリックから情報を受け取りました。アプリは、インターネット上のサービスからもデータを受け取れます。今日はその入口として外部APIを試します。

**授業用API候補（事前に3〜5個に絞り、実行環境で確認）**

| 候補 | データ | アプリCの例 |
|---|---|---|
| Open-Meteo | 気温・天気・風速等 | 天気表示・気温比較 |
| Open Library | 書籍情報 | 本の検索・表示 |
| PokéAPI | ポケモン関連データ | 名前・タイプの検索表示 |
| Art Institute of Chicago API | 美術作品の情報 | 作品情報を表示する図鑑 |
| The Met Collection API | 美術品情報 | 美術作品を調べるアプリ |

**利用前に伝える注意点**：APIごとに規約・料金・レート制限・APIキー・出典表示・著作権／画像ライセンスが異なる。キーなどの秘密情報をブラウザのコードへ埋め込まない。授業用候補は教員が使うエンドポイントと取得項目を事前検証する。

**基本方針**：学生は自由検索せず、動作確認済みの候補から1つ選ぶ。

### 158–167分｜③-1 APIのデータを読む

**教員が提示する簡略JSON例（架空）**

```json
{
  "temperature": 22,
  "weather": "sunny",
  "windSpeed": 3.5
}
```

**説明**：「項目名」と「値」。実際のAPIは入れ子の構造を持つこともあるため、ここでは考え方のみ扱う。

**学生の活動**：どの項目が気温・天気・風速かを特定する。

**Slack投稿**：「temperature：22（気温）」など読み取った3項目。

### 167–178分｜③-2 APIを実際に呼び出す

**学生の活動**：候補から1つ選び、提供されたURL・取得例を参考にAPIへアクセスして返却データを確認する。

**完成条件**：実際のAPIレスポンスから少なくとも1つの値を確認できること。

**Slack投稿**：利用API名、取得した項目・値、実際に取得できたことの証拠（画面等）。

**つまずいた場合**：エラーの内容を記録し、教員の動作確認済みサンプルまたは配布JSONを使って次へ進める。ただし模擬データを実際のAPI取得と区別する。

### 178–190分｜③-3 APIを使った別アプリCを作る

**学生の活動**：新しいアプリを作成し、選んだAPIのデータの一部を表示する。例えば都市ごとの天気、書籍検索結果、作品情報など。

**完成条件**：取得した情報をアプリ画面に表示できること。データの加工・表現上の工夫は発展課題。

**Slack投稿**：アプリ画面＋「どのAPIから何を取得し、何を表示したか」。

### 190–193分｜③のまとめ

**話すこと（例）**

> データの取得元が変わるだけで、同じWebアプリでも新しい機能を作れます。今回は外部のデータを読む・取得する・表示する、という3段階を体験しました。

**理解確認**：「今日使ったデータはどこにあり、どうやってアプリに届いた？」

### 193–200分｜ラップアップ・次回と次々回の予告

**振り返る3つの方法**

1. 入力の幅：マイク・センサーなど。
2. 表現の幅：入力・処理・出力、操作に対する反応、画像素材。
3. データの幅：外部API。

**話すこと（例）**

> 次回とその次の授業では、テーマを自由に決めてアプリを作ります。今日のどれか1つを使ってもよいし、組み合わせても構いません。今のうちに作ってみたいものを3つ以上考えておきましょう。

**学生の活動**：アプリアイデアを3案以上記録し、最も興味がある案に印を付ける。各案は「何を作る／誰が使う／何ができる」の簡単なメモでよい。

**Slack投稿**：アプリアイデア3案以上（必要に応じて最有力案に印）。
